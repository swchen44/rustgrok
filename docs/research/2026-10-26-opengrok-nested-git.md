# OpenGrok 1.14.20：多 repository project 與巢狀 Git 原始行為

研究日期：2026-10-26（Asia/Taipei）。固定基線：`oracle/opengrok` commit `3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3`，對應已確認的 OpenGrok 1.14.20。範圍：repository 發現設定、檔案歸屬，以及 history／annotate（blame）／diff 呼叫鏈。

**驗證狀態：STATIC_SOURCE_REVIEW；oracle runtime、上游 tests、Rust 產品 tests 均為 NOT_RUN。** 本文不是功能 PASS、效能結果或新實作政策。研究透過官方 GitHub 固定 commit 頁面及同 commit 的 raw source；沒有啟動 OpenGrok、JGit 或索引器。

## 1. 需求與結論界線

使用者已確認10個 project、每 project source 約50 MB；一個 project 可含多個 Git repo，亦可能 git-in-git。總 source 約500 MB 是估算；MB 單位、history 體積與每 project repo 數尚未指定。沒有既有 XML、客製 JAR、API scripts 或書籤需要搬移，不等於刪除原版內建能力。這些需求來源見[決策表](../08-decision-register.md)與[需求](../02-requirements.md)。

固定 source 可以確認：

- **project 與 repository 分開。** Project 以來源路徑識別；repository 由獨立 discovery／configuration map 登記，並從所屬 project 繼承 history 等設定。不是一個 project 只能有一個 repo。見 [Project.java L589–635](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/configuration/Project.java#L589-L635)、[RepositoryInfo.java L408–433](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryInfo.java#L408-L433)。
- **Git 可以作為外層及巢狀 repo，但 discovery 有兩個獨立上限。** `scanningDepth` 預設3；`nestingMaximum` 預設1。不能寫成無限遞迴。見 [Configuration.java L227–233](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/configuration/Configuration.java#L227-L233)、[L599–615](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/configuration/Configuration.java#L599-L615)、[GitRepository.java L412–434](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/GitRepository.java#L412-L434)。
- **檔案歸屬查已登記的 repository map。** 呼叫鏈由檔案路徑向父層找匹配，包含 canonicalization 與 cache；不是每次 history／blame 都向下掃描新的 `.git`。一般無 symlink 的穩定布局中，已登記內層 repo 的匹配先於外層；這是 source 控制流程的結論，不是自行創造的「最近 root」產品規則。見 [HistoryGuru.java L1331–1333](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/HistoryGuru.java#L1331-L1333)、[RepositoryLookupCached.java L73–137](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryLookupCached.java#L73-L137)。
- **history／annotate／revision retrieval 使用選中的 repo。** Web diff 先各自取得兩邊 revision 內容，再產生文字差異；不能用一次 project-wide Git command 代替。詳見第4節的逐層來源。

以上僅處理已知 Git 使用情境。原版 factory 同時列有其他 SCM，這份研究不把最終產品縮成 Git-only。見 [RepositoryFactory.java L54–78](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryFactory.java#L54-L78)。

### 2.2 掃描呼叫鏈

`Indexer.prepareIndexer` 先建立 projects，再呼叫 `env.setRepositories(searchPaths...)`；後者經 `HistoryGuru.addRepositories` 收集 RepositoryInfo。projects 先建立，是因 repo 會繼承 project 屬性。見 [Indexer.java L1138–1153](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/index/Indexer.java#L1138-L1153)、[RuntimeEnvironment.java L829–839](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/configuration/RuntimeEnvironment.java#L829-L839)。

每個起點的剩餘目錄預算是 `env.getScanningDepth() - levelsBelowSourceRoot`；這不是相對該起點重新給完整深度。遞迴收到負數會丟 IllegalArgumentException。見 [HistoryGuru.java L884–888](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/HistoryGuru.java#L884-L888)、[L979–1005](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/HistoryGuru.java#L979-L1005)。

在每個目錄，先用 `RepositoryFactory.getRepository(file, INDEXER, isNested)` 辨識。未辨識為 repo 時，只有剩餘 depth>0 且 PathAccepter 接受才進子目錄，depth減1、nesting不減；已找到 repo 則登記，再要求 nesting>0、depth>0、該 SCM 支援 subrepositories 才進子目錄，並把 nesting、depth各減1、isNested設true。Git 的 `supportsSubRepositories()` 與 `isNestable()` 均回true；factory 在巢狀模式只考慮可 nest 的類型。見 [HistoryGuru.java L894–952](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/HistoryGuru.java#L894-L952)、[RepositoryFactory.java L193–208](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryFactory.java#L193-L208)、[GitRepository.java L412–434](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/GitRepository.java#L412-L434)。

啟用 projects 時，factory 拒絕「repo root 正好等於 source root」的候選；不能把 source root、project root、repo root 三者強制合一。見 [RepositoryFactory.java L201–206](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryFactory.java#L201-L206)。

### 2.3 Git repo 辨識與 .git file

Git 的辨識條件是候選目錄直接含有存在的 `.git` 路徑；此處不要求 `.git` 一定是目錄，註解明指 submodule 的 `.git` file。開啟 JGit repo 時，`.git` directory 走 FileRepositoryBuilder.create；file 則讀 `gitdir:`，相對路徑以候選 repo root 為基準解析後設定 workTree/gitDir。見 [GitRepository.java L412–419](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/GitRepository.java#L412-L419)、[L714–752](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/GitRepository.java#L714-L752)。

「獨立 nested repo」、「Git submodule」、「linked worktree」不能只因都有巢狀目錄就視為同一 fixture。`.git` file 路徑有明確程式分支，**完整 linked-worktree 行為仍未由本輪證明**。上游 `testSubmodule` 覆蓋 submodule factory 辨識及 absolute/relative gitdir，但本輪沒有執行該測試。見 [GitRepositoryTest.java L820–864](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/test/java/org/opengrok/indexer/history/GitRepositoryTest.java#L820-L864)。

## 3. 每個檔案的 repository 歸屬

1. `HistoryGuru` 建構子選 `RepositoryLookup.cached()`。登記時以 repo directory name 作 repositories map key，另存 repo root 的 parent 至 repositoryRoots。見 [HistoryGuru.java L130–136](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/HistoryGuru.java#L130-L136)、[L1471–1476](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/HistoryGuru.java#L1471-L1476)。
2. `HistoryGuru.getRepository(file)` 委派 lookup，傳入已登記 roots、repository map 與 `PathUtils::getRelativeToCanonical`。cached implementation 先準備 potential parent roots，再由原 path 向父層走；每層先查該 path 的 map key，再嘗試 canonicalized 形式，直到第一個非空結果。見 [HistoryGuru.java L1331–1333](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/HistoryGuru.java#L1331-L1333)、[RepositoryLookupCached.java L73–137](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryLookupCached.java#L73-L137)、[L150–206](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryLookupCached.java#L150-L206)。
3. 目錄→repo 查詢結果會回填 cache；來源註解明示 filesystem 改變時可能回傳 stale result，失效／移除時才清 cache。因而「加入新 nested repo 後馬上自動重歸屬」不能由穩定布局的流程外推。見 [RepositoryLookupCached.java L57–65](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryLookupCached.java#L57-L65)、[L209–217](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryLookupCached.java#L209-L217)。

**靜態推導的例子**：若 `/P/outer` 與 `/P/outer/inner` 都已登記，對後者內的檔案，正常父層遍歷先遇到 inner。若 inner 因 depth／nesting 未被登記，lookup不會臨時建立它，可能匹配 outer；此時得到的 history／blame 是否存在，取決於 outer 的實際 tracked tree，不能捏造 inner 的 revision。symlink、deleted paths、cache 變動需另以 oracle 實跑。

上游 `RepositoryLookupTest.testLookups` 本身包含巢狀 repo 與 symlink，並對 cached、uncached lookup 比較所屬 repo；這是上游測試規格存在的證據，**不是本輪 PASS**。見 [RepositoryLookupTest.java L93–114](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/test/java/org/opengrok/indexer/history/RepositoryLookupTest.java#L93-L114)、[L217–226](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/test/java/org/opengrok/indexer/history/RepositoryLookupTest.java#L217-L226)。

**目錄 history 的限制（靜態推導）**：上述 history route 查 enclosing repo，沒有往下聚合 project 內所有 sibling repos。若 project目錄本身不是repo、父層也沒有已登記repo，這條route得到null／404；若 project root 本身是outer repo，目錄history來自outer，不能直接推成會聯集 inner 的獨立 commits。這是所讀call-chain的範圍，不表示 UI 的repository listing或其他頁面都沒有多repo資訊；實際頁面結果仍待 oracle。

Git history 的中間層是 `RepositoryWithHistoryTraversal.getHistory(file,since,till,count)`：建立帶 merge 設定的 HistoryCollector，呼叫 subclass 的 traverseHistory，再組成 History；不是由方法名稱推測連線。見 [RepositoryWithHistoryTraversal.java L106–118](https://github.com/oracle/opengrok/blob/3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3/opengrok-indexer/src/main/java/org/opengrok/indexer/history/RepositoryWithHistoryTraversal.java#L106-L118)。
