# Rustgrok path postings

This production library component builds an **in-memory**, single-project inverted path-token index over a complete logical-path manifest supplied by the caller. It uses `rustgrok-analysis` for indexing and one-term candidate lookup. `PathSnapshot::lookup` returns an unordered `HashSet` of candidates; it is not an OpenGrok-ranked search result and must not be presented as one. Wildcards, operators, path separators, dot syntax and other unimplemented query syntax return `UnsupportedQuery`, not a misleading empty result. Supported Unicode is limited by the analysis crate.

`PathIndex::new(project, limits)` requires explicit maximum document count, individual path bytes, cumulative path bytes and live generation count; no product SLO or default capacity is selected. Limits apply after each iterator item is received and cannot constrain memory allocated inside the caller's iterator. Logical paths must be absolute slash-separated paths under the exact project component; empty, dot, dot-dot and backslash components are rejected. This validation is an explicit restricted API contract, not a claim that OpenGrok applies the same source filters. The library does not discover files, follow symlinks, determine repo membership, read source contents or modify source. The caller must supply the entire authoritative manifest and its expected count; count mismatch, duplicate paths, unsupported input, I/O/invalid-data errors and cancellation all fail without publishing. The component cannot detect a provider that falsely claims an incomplete list is complete. A real source scanner and original same-configuration path/filter behavior remain blocked work.

A successful replacement atomically publishes one immutable generation; snapshots keep the preceding generation available during and after replacement. `manifest()` retains the exact caller-supplied paths for that generation in memory. The live-generation cap is at least two; if an older reader retains enough generations to reach the cap, a subsequent build returns `LimitExceeded` until readers release them. Caller-held candidate-set copies and allocations inside the source iterator are outside this component’s limits. Two writers cannot build concurrently: the second receives `WriterBusy`. The caller supplies the last observed generation ID; an out-of-date ID returns `StaleGeneration`, preventing a delayed build from overwriting a newer one. A source iterator panic leaves current readers available and poisons the writer lock, so later writes fail closed.

Each publication attempt takes a `CancellationToken`. Its `cancel()` returns `true` if cancellation wins; a successful cancellation prevents that generation from being published. It returns `false` once publication has atomically begun. Cancellation is cooperative between iterator calls and cannot interrupt an iterator blocked on I/O. The `PathIndex` itself is in-memory. The separate constrained durable wrapper described below provides restart recovery on macOS; it does not implement the complete Q8 publication contract. Source reading, raw/download, xref and history are outside this library and no reading snapshot is created, consistent with Q9. Other languages, SCM, multiple projects, sorting, GUI and browser tests remain required.

## macOS durable wrapper

`durable::DurablePathIndex` is a single-project, single-process-at-a-time component. The caller supplies a complete manifest and count; a dishonest or faulty caller can still pass a valid but incomplete list. No source discovery, source content, xref, history, cross-project publication, or ranked search is implemented. The wrapper binds its new private store to the source directory device/inode and project; moving or replacing that directory requires a new store. It rejects relative paths, symlinks and source/store overlap, and uses an exclusive OS advisory lock. It retains the opened source directory descriptor and its original path-component identities; it rechecks them when opening, before and after obtaining a snapshot, before building/writing, and immediately before publication. A missing, moved or replaced source path yields `SourceChanged`; already-held snapshots remain readable. A detected replacement before a build writes no generation; a replacement detected after preparation can leave unpublished generation/pointer files. These checks cannot atomically prevent a source rename between the last check and publication, or prove that a supplied manifest belongs to that source. Callers must coordinate source-path/ancestor replacement for the duration of each operation, including snapshot and publication; changes to contents during indexing are not stabilized. A malicious same-user concurrent rename remains outside the verified boundary. The store and its parent must be controlled by the same trusted user; concurrent malicious changes by that user, including renaming directories or replacing the lock, are outside this contract. Checksums detect accidental corruption, not deliberate authenticated tampering.

Before publication it validates and synchronizes an immutable, checksummed generation and a checksummed pointer. A same-directory rename changes `CURRENT`, followed by a directory sync; existing snapshots and readers retain the old generation while that sync runs. If sync fails after rename, `PublicationIndeterminate` means the durable outcome is unknown: that handle refuses new snapshots and writes, including a writer that passed its first check before the failure and acquired the writer lock afterwards. Existing snapshots remain usable. Close and reopen to validate and sync the actual pointer and generation before continuing; do not assume the old generation survived. Earlier errors leave the previous pointer in place. Cancellation wins only before publication begins. Immutable old files and interrupted orphan files are retained, never automatically deleted; `max_generation_id` bounds attempted names and eventual exhaustion requires caller intervention. Live snapshots still count against the configured memory generation limit.

Native correctness and process-exit injection were tested on macOS only. `sync_all` and rename rely on the operating system and filesystem; no physical power-loss test or `F_FULLFSYNC` guarantee was established. Linux and Windows behavior is not implemented or validated here. Simulated disk-full errors do not establish actual full-disk behavior. Fault injection is feature-gated for tests and must not be enabled in a production build. See [durable evidence](../../tests/evidence/durable-path-2026-11-03/README.md).
