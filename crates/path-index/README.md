# Rustgrok path postings

This production library component builds an **in-memory**, single-project inverted path-token index over a complete logical-path manifest supplied by the caller. It uses `rustgrok-analysis` for indexing and one-term candidate lookup. `PathSnapshot::lookup` returns an unordered `HashSet` of candidates; it is not an OpenGrok-ranked search result and must not be presented as one. Wildcards, operators, path separators, dot syntax and other unimplemented query syntax return `UnsupportedQuery`, not a misleading empty result. Supported Unicode is limited by the analysis crate.

`PathIndex::new(project, limits)` requires explicit maximum document count, individual path bytes, cumulative path bytes and live generation count; no product SLO or default capacity is selected. Limits apply after each iterator item is received and cannot constrain memory allocated inside the caller's iterator. Logical paths must be absolute slash-separated paths under the exact project component; empty, dot, dot-dot and backslash components are rejected. This validation is an explicit restricted API contract, not a claim that OpenGrok applies the same source filters. The `PathIndex` API does not discover files, follow symlinks, determine repo membership, read source contents or modify source. The caller must supply the entire authoritative manifest and its expected count; count mismatch, duplicate paths, unsupported input, I/O/invalid-data errors and cancellation all fail without publishing. The component cannot detect a provider that falsely claims an incomplete list is complete. A separate restricted source scanner is described below; complete same-configuration path/filter behavior remains blocked work.

A successful replacement atomically publishes one immutable generation; snapshots keep the preceding generation available during and after replacement. `manifest()` retains the exact caller-supplied paths for that generation in memory. The live-generation cap is at least two; if an older reader retains enough generations to reach the cap, a subsequent build returns `LimitExceeded` until readers release them. Caller-held candidate-set copies and allocations inside the source iterator are outside this component’s limits. Two writers cannot build concurrently: the second receives `WriterBusy`. The caller supplies the last observed generation ID; an out-of-date ID returns `StaleGeneration`, preventing a delayed build from overwriting a newer one. A source iterator panic leaves current readers available and poisons the writer lock, so later writes fail closed.

Each publication attempt takes a `CancellationToken`. Its `cancel()` returns `true` if cancellation wins; a successful cancellation prevents that generation from being published. It returns `false` once publication has atomically begun. Cancellation is cooperative between iterator calls and cannot interrupt an iterator blocked on I/O. The `PathIndex` itself is in-memory. The separate constrained durable wrapper described below provides restart recovery on macOS; it does not implement the complete Q8 publication contract. Source reading, raw/download, xref and history are outside this library and no reading snapshot is created, consistent with Q9. Other languages, SCM, multiple projects, sorting, GUI and browser tests remain required.

## macOS durable wrapper

`durable::DurablePathIndex` is a single-project, single-process-at-a-time component. The caller supplies a complete manifest and count; a dishonest or faulty caller can still pass a valid but incomplete list. Source discovery is limited to the scanner described below. Source content, xref, history, cross-project publication, and ranked search are not implemented. The wrapper binds its new private store to the source directory device/inode and project; moving or replacing that directory requires a new store. It rejects relative paths, symlinks and source/store overlap, and uses an exclusive OS advisory lock. It retains the opened source directory descriptor and its original path-component identities; it rechecks them when opening, before and after obtaining a snapshot, before building/writing, and immediately before publication. A missing, moved or replaced source path yields `SourceChanged`; already-held snapshots remain readable. A detected replacement before a build writes no generation; a replacement detected after preparation can leave unpublished generation/pointer files. These checks cannot atomically prevent a source rename between the last check and publication, or prove that a supplied manifest belongs to that source. Callers must coordinate source-path/ancestor replacement for the duration of each operation, including snapshot and publication; changes to contents during indexing are not stabilized. A malicious same-user concurrent rename remains outside the verified boundary. The store and its parent must be controlled by the same trusted user; concurrent malicious changes by that user, including renaming directories or replacing the lock, are outside this contract. Checksums detect accidental corruption, not deliberate authenticated tampering.

Before publication it validates and synchronizes an immutable, checksummed generation and a checksummed pointer. A same-directory rename changes `CURRENT`, followed by a directory sync; existing snapshots and readers retain the old generation while that sync runs. If sync fails after rename, `PublicationIndeterminate` means the durable outcome is unknown: that handle refuses new snapshots and writes, including a writer that passed its first check before the failure and acquired the writer lock afterwards. Existing snapshots remain usable. Close and reopen to validate and sync the actual pointer and generation before continuing; do not assume the old generation survived. Earlier errors leave the previous pointer in place. Cancellation wins only before publication begins. Immutable old files and interrupted orphan files are retained, never automatically deleted; `max_generation_id` bounds attempted names and eventual exhaustion requires caller intervention. Live snapshots still count against the configured memory generation limit.

Native correctness and process-exit injection were tested on macOS only. `sync_all` and rename rely on the operating system and filesystem; no physical power-loss test or `F_FULLFSYNC` guarantee was established. Linux and Windows behavior is not implemented or validated here. Simulated disk-full errors do not establish actual full-disk behavior. Fault injection is feature-gated for tests and must not be enabled in a production build. See [durable evidence](../../tests/evidence/durable-path-2026-11-03/README.md).

`src/lib.rs`, `src/durable.rs` and `tests/durable.rs` are independent MIT code; see [MIT notice](RUST-LICENSE-MIT.txt). `src/durable/scanner.rs`, `tests/source_scanner.rs` and `tests/generation.rs` retain CDDL-1.0 provenance and copyrights from the pinned OpenGrok indexer and `IndexerTest` and are distributed with [LICENSE](LICENSE.txt) and [NOTICE](OPENGROK-NOTICE.txt). The analysis dependency has its own CDDL/MIT scopes. Original source hashes and limited test evidence are in [path-index evidence](../../tests/evidence/path-index-2026-11-03/README.md).

## Restricted source scanner

On macOS, `DurablePathIndex::replace_from_source` walks the bound source project and publishes a path generation with the existing single-writer and cancellation protocol. It supports only the fixed original configuration evidenced in [scanner evidence](../../tests/evidence/source-scanner-2026-11-03/README.md): ordinary lowercase ASCII directory names and `.c`, `.py`, `.js` regular files with lowercase ASCII names, digits, `_`, `-` and `.`. A `.git` regular file or directory is ignored by name, matching the original captured global enabled-adapter filter; this does not identify or assign repository ownership. All other hidden names, unsupported extensions/names, symlinks, special files and unreadable entries return an error and preserve the previous generation. Directory entries are bounded by `8 * max_documents + 128` and directory nesting by 128; document/path/cumulative-path limits also apply. No source file or reading snapshot is written, and no source contents, SCM metadata, Ctags output, history or ranking is indexed. This is a strict subset, not a general OpenGrok source filter or a product-complete scanner.

The walker uses directory-relative no-follow opens and compares observed file/directory metadata again immediately before publication. It detects the tested persistent additions, deletions and metadata/content changes; metadata is not a content hash, so the comparison cannot prove unchanged bytes or detect changes undone between checks. The caller must coordinate all source, source ancestor and content changes throughout scanning and publication. A change after the final check is not excluded atomically. Without that external coordination, consistent indexing and full Q8 remain unverified. Existing snapshots remain readable during the scan. macOS behavior only was tested; there is no Linux or Windows implementation.

## Fixed-registry multi-project manifest batch

On macOS, `durable::batch::DurableBatchIndex` is an additional, separately marked store and API. Its caller supplies one complete logical path manifest and expected count for each project in an explicit fixed registry. On the first successful batch, that registry is established; later replacements require exactly the same set. Subset updates, additions, removals, and arbitrary job selection are explicitly unsupported by this first API and are not product-policy decisions. A single durable generation and pointer contain the entire registry and all paths. The writer validates every project using the existing path index before attempting publication. An input error, cancellation, stale generation or rejected limit publishes none. A second in-process writer and a second process opening the store fail with `Busy`. Existing single-project stores are neither migrated nor accepted as batch stores; ordinary single-project open rejects the batch marker.

A `BatchSnapshot` holds one immutable batch generation. `lookup` and `lookup_expression` select one named project and reconstruct that project's original logical paths before using the existing analysis and query APIs; results are complete unordered sets for that project, not ranked cross-project results. An unknown project is rejected. Internal container prefixes and registry markers are never exposed as source paths or query tokens. Project reconstruction and registry validation share one nonblocking per-handle scratch lock; a concurrent scratch operation may return `Busy`. The caller must retain the batch snapshot to compare projects consistently across a publication. `BatchLimits` requires explicit per-project and aggregate limits and caps them at 64 projects, 50,000 source paths, 16 MiB source-path bytes, 4,096 bytes per path, and 16 live generations. Caller allocations, returned result sets and blocked caller iterators are outside those limits.

The explicit-manifest `replace` API reads no source content or source directory entries. The scanner-based API described below reads directory entries but not source contents. The batch store binds one source-root directory identity and uses the existing descriptor-relative source/store isolation and durable publication protocol, but it cannot establish that the supplied manifest is complete or corresponds to a stable source tree. The caller must coordinate source and ancestor changes; metadata or final checks do not defeat a malicious same-UID rename race. A restricted direct CLI is available; the batch store does not expose host, Web, SCM, related data, full Q8, general multi-project query semantics or a product migration. Physical power loss, `F_FULLFSYNC`, Linux and Windows remain unverified. Feature-gated process exits and sync failures exercise limited crash/recovery states, not power loss. See [batch evidence](../../tests/evidence/batch-publication-2026-11-03/README.md). `src/durable/batch.rs` and `tests/durable_batch.rs` are independent MIT code; existing CDDL and third-party notices remain unchanged.


`DurableBatchIndex::replace_from_source` additionally accepts an explicit list of project names mapped to direct child directories of the bound source root. It reuses the existing restricted scanner, rejects duplicate or invalid names and aliased/symlink directories, observes all selected projects before building, then re-observes all immediately before the single batch commit. Per-project limits apply alongside aggregate document/path-byte limits and an aggregate directory-entry budget of `8 * max_batch_documents + 128 * project_count`. Aggregate checks run after each project, so rejection may follow up to one additional per-project scan budget. Cancellation is cooperative between scanner entries and cannot forcibly interrupt blocked filesystem operations. Source and ancestor mutations must still be externally coordinated; observed metadata is not a content hash, and a post-validation race remains possible. Unlisted root entries are outside the explicit job, not discovered or declared indexed. The fixed-registry restriction and non-migration of single stores remain; no batch host, reading snapshot, SCM history or full Q8 is implied.
