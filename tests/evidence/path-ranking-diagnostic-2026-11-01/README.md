# Path query and ranking diagnostic

This diagnostic reads the pristine original index independently created from the same verified public corpus; it is **not** the specific original index used for the recorded performance run. `RustgrokScoreProbe.java` invokes the pinned OpenGrok QueryBuilder and Lucene 9.12.3 against a MultiReader (alpha then beta), without the original full SearchEngine executor. `diagnostic.json` lists the exact index files and hashes, helper source hash, candidate input hash and commands. The captured raw stdout and stderr preserve the score explanations.

For `path=main`, the original builds `TermQuery(path:main)` and returns three documents. All three have exactly score `0x1.fdc71cp-3`, with global docIDs 8/9/10 in the order alpha C, beta C, beta Python on **this index**. The independent earlier HTTP capture's first two pages happen to show the same order, but the indexes are different and this observation cannot explain that performance run's exact ordering. Other cases include non-equal original scores, so this tie result is not a general tie policy. The candidate scan retains its own ingestion order and does not implement score or original docIDs; multi-project paging remains incompatible.

For `path=mai` (and independently `path=ain`), the reference QueryBuilder creates an exact term query and returns no documents, while the former Rust substring scan returned three. The test was run red against `mai.oracle.txt`, then the candidate's restricted path matcher was changed to use upstream-derived path tokens and conjunction. `mai.candidate-before.json` and `mai.candidate-after.json` preserve the actual before/after output. The fixed OpenGrok PathTokenizer also emits a dot token and lowercases path terms; the CDDL-scoped port and its source/copyright references are in `src/path_response.rs`. This is a narrow experiment: it does not implement the complete Lucene parser, Unicode equivalence across runtimes, all special syntax, relevance scoring, original indexing/docID order, or general path compatibility.

For future scorer work, local Tantivy 0.27.0 `src/query/bm25.rs` uses `Searcher::total_num_docs` based on segment `max_doc` and multiplies its IDF weight by `1 + K1`; the captured original explanation reports the number of documents **with the path field** (`N=5`) even though this MultiReader has `maxDoc=16`, and its displayed term formula omits that multiplier. These observations are not proof that a constant rescaling gives Lucene-compatible ordering: sparse fields, field lengths, float rounding, query structure, and docID tie ordering must be tested against the original. The Tantivy experiment remains a candidate, not an adopted engine.
