# Local host startup diagnosis

The independent reviewer at `514e342b6f875ec5a71dabcad1a6e317fe3fecbc` observed the default suite fail 11/12 host tests and then the isolated `oversized_query_response_returns_error_not_partial_results` fail again. Both timed out waiting five seconds for startup readiness with empty child stderr; neither reached the result-limit assertion. The two reviewer streams are retained here, with their hashes and a derived receipt subset. The complete original receipt is retained locally at the path in that subset; it is not part of this repository. The reviewer's binary identity and complete background environment were not recorded.

In this session, the recorded `TMPDIR`, Cargo target and job count were matched. Four pre-change exact Cargo runs and ten serial direct-harness runs passed; one exact run's streams are retained here, and the other local debug records are not all included in this repository. These results do not explain or invalidate the historical failures. The five-second limit is a test-runner deadline, not an approved product startup SLO.

A single successful diagnostic run printed stage markers through store decode, recovery sync, socket binding and readiness flush. Its streams are retained here; its temporary diagnostic source is identified in `receipt.json` and is not committed product code. This observation identifies the stages reached in that run only; it does not identify the cause of either historical timeout. No performance profiling or benchmark was performed.

The separate, reproducible test-harness issue was that a panic after spawning a child but before `Host` construction could leave that child running. A regression using an intentionally stopped child first failed without the guard and passed with it; the red output was not saved as a raw stream. The test-only guard now attempts to terminate and reap a child on setup panic; another intentionally stopped-child test exercises the existing five-second timeout branch and checks the cleanup report. The injection does not reproduce or explain the reviewer timeout. Cleanup remains subject to operating-system errors or blocking; timeout diagnostics report cleanup failure rather than waiting for unread stderr when reaping failed. No product startup behavior or timeout was changed.

After the test-only change, the serial default suite passed CLI 3/3 and host 14/14; the test-hooks suite passed CLI 5/5 and host 22/22. The original exact case also passed separately. Raw streams, inputs, commands, and output hashes are in `receipt.json`. The two corresponding product binaries were verified against the locally retained bytes at the recorded cache paths immediately after each suite. Those bytes and the complete reviewer receipt are local, not distributed with the repository. These results do not show that the unexplained historical timeout has been fixed. The long-lived host remains a limited macOS single-project path-only development slice; full Q8 and product compatibility are not established.
