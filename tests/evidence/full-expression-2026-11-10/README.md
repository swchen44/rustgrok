# Bounded FULL expression comparison, 2026-11-10

Issue #6: macOS arm64, OpenGrok 1.14.20 commit `3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3`. The original indexer, parser and Tomcat HTTP endpoint ran independently before Rustgrok; these are correctness observations, not performance measurements or product acceptance. Five synthetic C comments contain the ASCII components of their distinct file paths. `receipt.json` records configuration and verified archive, JDK, JAR, WAR, ctags and response hashes; the 21 original HTTP bodies and parser stdout/stderr are retained without sorting. The last five single-term HTTP requests establish coverage of each source. `artifact-sha256.json` binds these retained files.

`probe.py` and `PathQueryOracle.java` are the exact executed capture scripts, retained as evidence, not portable reproduction commands: they reference the then-current integration checkout and `/tmp/rustgrok-full-expression-probe`. The probe is adapted from `tools/capture_path_query_oracle.py`; its Java adapter calls `QueryBuilder.setFreetext`. The synthetic comment content is `/* ` followed by path components separated by spaces and `.c` removed, followed by ` */` and LF. Original HTTP input is `full`, scoped to project `demo`. Results retain original ranking in raw bodies; the Rust test compares candidate sets only. The case `alpha OR beta AND gamma` was observed but is explicitly rejected by this bounded implementation rather than approximated.

The Rust public CLI test creates the same five `demo` documents plus a second project and checks implicit AND, OR, NOT, grouping and pure negative cases after reopening the store. The host test covers project isolation and unsupported syntax; a separate controlled publication test checks the expression against old and new generations. These tests do not establish complete grammar, positions for multi-term results, ranking, Web, Linux/Windows, or any full-product acceptance. Only the original cases covered by the tests are claimed as compared.
