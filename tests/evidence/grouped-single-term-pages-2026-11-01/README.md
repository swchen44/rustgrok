# Project grouping and page projection: restricted G1 scorer

The fixed OpenGrok SearchEngine constructs its multi-project reader using project names in Java TreeSet order; the derived CDDL-scoped project comparator in the candidate uses UTF-16 code-unit order and preserves candidate ingestion order **within** each project. This models the independently verified cross-project ordering rule; it does not copy any original docID or force the original indexer to run with different concurrency.

For the single `full=main` query, both project argument orders and six page requests per order (full page, three one-hit pages, zero-sized page, and out-of-range page) are compared to original HTTP responses from `project-order-boundaries-2026-11-01`. Each original and candidate output is saved untouched; comparison.json compares only resultCount, page bounds and ordered paths. All 12 projections match in these particular index generations. The original REST snippets/tags/status semantics are not implemented by the candidate CLI, and this is not full HTTP or general ranking parity. Earlier original independent index generations show different order for same-project equal-score JavaScript hits; candidate project-internal ingestion remains independent, so this finite projection cannot resolve that gap.

The original raw observations can be rerun from a verified retained public capture with `python3 tools/capture_project_order.py --capture CAPTURE_DIR --output NEW_EXTERNAL_DIR`; it copies the index and changes only the copied dataRoot and loopback listener, retaining original defaults. Candidate invocations use `--field full --query main --project NAME` for both projects, `--lucene-single-term`, and explicit `--start` / `--maxresults`; the current public CLI test records both argument orders and boundaries. Neither this comparison nor the independent original ordering observations are performance results.

The exact candidate input bytes, including ingestion order, are preserved in [`../lucene-single-term-2026-11-01/candidate-documents.json`](../lucene-single-term-2026-11-01/candidate-documents.json), SHA-256 `51f7f42c70eb4c2184c5e19ac1e9f329023ea3be865fb3accb8644c4597315d5`. All five `content` values were separately checked byte-for-byte against the corresponding verified public corpus files. Replaying the retained input against the candidate reproduced all 12 saved count/page/path projections. The retained input makes candidate replay possible; it cannot reconstruct the original unretained index generation or original document IDs. An independent check with reversed candidate ingestion order exchanged two equal-score alpha JavaScript hits; same-project tie compatibility is not resolved.
