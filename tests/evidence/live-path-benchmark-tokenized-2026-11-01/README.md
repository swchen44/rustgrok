# Live path-only HTTP experiment: limited observed response and session slice

On the same Mac, the independent original OpenGrok 1.14.20 JDK/Tomcat and the Rust release spike ran against the 3,969-byte public corpus. The original had `allowMostPopular=false`, an explicit deviation from its default for the deferred suggestions feature. The exact query was `path=main.c&projects=alpha&start=0&maxresults=10`, a single-result path query. JVM flags, hashes, configuration, platform, input/index sizes and resource snapshots are in metadata.json and resources.json.

Before warming or measuring, both endpoints returned HTTP 200, the same ordered JSON except top-level `time`, and `JSESSIONID` cookies with the same name and attributes (`Path=/source; HttpOnly`). A follow-up request to each endpoint carrying its own cookie returned HTTP 200, no new cookie, and the same body apart from time. The gate redacts only the random 32-hex-digit JSESSIONID value, compares its name and attributes, and checks all response headers except Date, Content-Length and Connection. It repeats the status, body, and selected header checks for every warmup and measurement response. Raw response bodies, sanitized headers, all sample latencies and the report are preserved under run/. Session values are never saved. Session timeout, capacity, authorization plugins, and other session semantics have not been established as equivalent; the Rust experiment has a 10,000-session limit and does not expire sessions. The user excluded role and project ACL requirements; this experiment does not implement login, roles or ACL.

After 20 warmup requests per endpoint per load, the client sent 50 requests per endpoint at one client and 50 per endpoint in batches of five simultaneous clients. Each client kept its own session cookie in memory across requests, and every timed request opened a new connection. Endpoints were measured sequentially rather than loaded simultaneously. Percentiles use nearest rank. All 200 measured HTTP responses passed the above checks, with zero recorded errors/timeouts:

| Clients | Endpoint | Samples | p50 ms | p95 ms | p99 ms |
| --- | --- | ---: | ---: | ---: | ---: |
| 1 | OpenGrok, allowMostPopular=false | 50 | 2.725 | 3.087 | 3.243 |
| 1 | Rust spike | 50 | 0.483 | 0.785 | 0.935 |
| 5 | OpenGrok, allowMostPopular=false | 50 | 3.852 | 4.842 | 4.986 |
| 5 | Rust spike | 50 | 1.121 | 1.511 | 1.589 |

These are observations of this limited operation, not a product-wide speed claim, SLO, general query parity, or a representative 500 MB/5-user workload. Background load, power state and OS caches were not controlled; both sides were warmed. The source fixture and the available API features differ greatly from production. Raw index sizes are 439,911 bytes for original and 5,414 bytes for the Rust JSON index, which cover different features and are not equal-function storage measurements. Only one 200 ms resource snapshot was obtained; it is not a peak or workload profile and cannot support a resource comparison.

Reproduction uses a fresh isolated `tools/capture_opengrok_baseline.py` capture and the matching scan index, then `python3 tools/run_live_path_experiment.py --oracle-capture CAPTURE_DIR --corpus PUBLIC_CORPUS --output NEW_EXTERNAL_DIR`. The runner builds both original and candidate indexes from the verified public corpus, verifies the original sourceRoot, and copies the fresh original index and configuration into an isolated working directory; capture-integrity.json records the matching pre-run, post-copy and post-run tree hashes. The runner previously modified a separate earlier capture during exploration; that capture was not used for these final measurements. It records the fresh original indexer receipt and candidate index command and hashes. Issue #7 remains open pending complete query/rank compatibility and representative Mac and native Ubuntu verification.

The original returned a new JSESSIONID for an invalid cookie and a new client; these limited observations and bodies are in session-followup.json. In a separate cross-project `path=main` query with `maxresults=1`, both start=0 and start=1 returned different ordered paths between original and candidate (paging-comparison.json). No general paging or ranking parity is claimed. Earlier exploratory runs used an independently supplied candidate index or created a new session on every sample; their results are retained locally only and are not the final same-corpus, persistent-user experiment.

The runner deleted the fresh original index, its working copy, and the candidate index after this run. metadata.json preserves their tree/file hashes and build commands, not the index bytes. Reproduction therefore requires reindexing and cannot establish the exact index generation or original docIDs used in this recorded run; those can vary even for identical source. The pristine input capture is separately retained outside the repository, but is not the index that was measured.

Subsequent review found the runner used for this recording connected via loopback but had not explicitly configured the Tomcat connector to bind only loopback, and had not disabled the shutdown port. The isolated corpus was public; the record does not establish whether another host connected. The runner and capture helpers now explicitly bind the connector to `127.0.0.1` and disable the shutdown port; an actual Tomcat process was separately observed with one TCP listener at `127.0.0.1:49236` using `lsof -nP -a -p PID -iTCP -sTCP:LISTEN`. This observation is a subsequent check, not part of the original timing run.

The original timing client could follow HTTP redirects before recording status. Therefore its saved 200 statuses do not establish that no redirect occurred; redirect history was not recorded. The corrected client rejects redirects and the reproduction tests cover that behavior. An independent subsequent check of all 200 retained raw timed response bodies found zero differences under strict recursive JSON type comparison, preserving result path order and removing only top-level `time`; `tests/contract/test_persisted_benchmark_evidence.py` repeats that check. This confirms the saved final bodies, not the unrecorded redirect history or a new performance run. The gate treats JSON booleans, integers, and floating-point numbers as distinct types; numerically equal float spellings such as `1.0` and `1e0` compare equal, while `1` and `1.0` do not. Non-finite parsed floating numbers are rejected.

The measurement used the path-token matcher Rust binary whose SHA-256 is in metadata.json. The earlier pre-token-matcher run is separately retained in live-path-benchmark-matched-2026-11-01.
