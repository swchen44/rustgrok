# FULL tokenizer and scorer investigation

The original diagnostic uses OpenGrok 1.14.20 / commit 3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3, its `CompatibleAnalyser` / `PlainFullTokenizer` and JFlexTokenizer, and Lucene from the fixed release. The original scorer diagnostic reads the independent pristine public index used for the path-ranking diagnostic, not the performance index. The original and candidate wrapper sources are `experiments/search-spike/oracle-diagnostics/RustgrokTokenProbe.java` and `experiments/tantivy-scorer-spike/examples/full_token_probe.rs`. Raw outputs and input hashes are retained here. The Java wrapper has no license assigned by the Rust/JS MIT policy; the Rust wrapper is independent MIT. The adapter is a scoped CDDL port of the pinned upstream lexer and JFlexTokenizer, with notices and copyright retained in the module and crate.

The original `full=__main__` query returns only the Python file; the old Tantivy default-tokenizer candidate returned all five public files. A public scorer CLI test was red on that output and green after adding the experimental FULL analyzer. This establishes only that query and corpus case. Before the adapter, the original token stream for the Python-like example emitted `main` at positions 1 and 11 and `__main__` as one term at position 9; Tantivy SimpleTokenizer emitted `main` at positions 1, 4, and 5 and omitted punctuation. The raw streams are `oracle-tokens.txt` and `tantivy-default-tokens.txt`.

`token-comparison.json` separates token ordinal positions from offsets: the original reports UTF-16 code units and Tantivy uses UTF-8 bytes. Identifier, punctuation and a 40,000-character ASCII identifier matched terms, positions and converted offsets in the recorded cases after adapting. The long token is truncated to 32,766 UTF-16 units while preserving the original end offset. The Unicode case includes an astral emoji followed by `abc`; that token's candidate byte offsets convert to the original UTF-16 offsets. For `İSTANBUL`, the lowercased token terms and ordinal match, but the original end is 37 UTF-16 units while the candidate byte end converts to 36. Four further lowercasing cases are in casefold-offset-comparison.json: the original end may exceed the source token boundary and overlap the next token, so neither offset is substituted for the other. For `a` repeated 32,765 times followed by U+10400, the original emits 32,766 UTF-16 units ending in an unpaired D801 high surrogate, with end offset 32,767; Lucene BytesRef is 32,768 bytes ending EFBFBD. The prior candidate silently produced only 32,765 `a` bytes. The G1 scorer and token diagnostic now reject this split before tokenization; whether original indexing accepts that bytes term is not established. Arbitrary supplementary-character boundaries remain unsupported, not equivalent. Unicode classification/version, case folding, offsets, and index handling of long non-ASCII terms require additional work. The input definitions and raw before/after outputs are preserved; these finite cases do not prove general equivalence.

`corpus-token-comparison.json` records 198 C, 245 Python and 223 JavaScript tokens, with the same terms and ordinal positions in each of these three small public files. Python `main` frequency is 2 on both. In the particular multi-project `full=main` case, original and adapted candidate both show Python freq=2, dl=232 and avgdl=217.4; their raw explanations are in the earlier original `score-other-cases/full_both.txt` and `full-both-adapted.json`. Tantivy still uses its own BM25 formula, floating-point operations, field statistics and index/document IDs. The original ranks alpha C before beta C when their scores tie in the captured original; this candidate ranks beta C before alpha C. There is no scoring or ranking parity claim, and this experimental analyzer does not select the product engine or apply to path, refs or definitions.

For reproduction, compile the Java wrappers with the fixed release `lib/*` on the classpath, then run `RustgrokTokenProbe` with each input in token-comparison.json and `RustgrokLongTokenProbe` for the split case. Run `cargo run --release --locked --offline --example full_token_probe -- INPUT` inside the Tantivy spike with the same input. Java offsets are UTF-16; the example prints Tantivy UTF-8 byte offsets. The latter rejects the unsupported split explicitly.

A separate original indexer run for the surrogate-boundary input and an 11,000-character CJK term is captured under `tests/evidence/long-token-indexer-2026-11-01`. Both whole processes returned exit 0 but each logged its only source file as failed and neither path query returned a hit; the split case's actual indexer failure was `IndexOutOfBoundsException` in the lexer, while the CJK case reported a 33,000-byte immense term. The candidate explicitly rejects both cases. This is a documented difference and not a correctness pass for dropped files.

Fixed-source inspection also found that Lucene computes IDF/average field length using field-specific document counts and double intermediates, and evaluates BM25 tf in a different floating-point operation order from Tantivy 0.27.0. Tantivy's statistics provider exposes a total document count without a field argument. Therefore neither globally dividing scores by 2.2 nor reranking only a native Tantivy top-K is an established general solution: the former can change ordering through rounding or mixed clauses, while the latter can discard documents needed by the target scorer. Exact statistics, all matching documents, query-family behavior and tie identity remain separate open work.
