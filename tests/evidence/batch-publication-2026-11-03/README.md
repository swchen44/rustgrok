# Fixed-registry multi-project path batch correctness

The user confirmed D12 on 2026-11-03: every project covered by the same indexing job must succeed before they are published together; failure or cancellation leaves that batch at its last successful version. The tested component is an initial restricted API that requires a complete, fixed registry and supplied path manifest on every replacement. It does not perform source scanning, support registry or subset changes, include xref/history or expose a CLI/host. It cannot verify that a caller-supplied manifest is complete or corresponds to actual source contents. The parent source root is bound and no source files are written. It does not implement full Q8, cross-project ranked search, Web or product compatibility. Original query/path behavior and its provenance remain documented in the preceding path-index and query evidence.

The batch is represented as one complete durable generation with one pointer publication. The component reconstructs original per-project paths before analysis and never treats its internal prefix as a query term. Public API tests cover two-project old/new views and held snapshots, complete-registry enforcement, name/path isolation, unsupported paths, input I/O, cancellation, stale and concurrent writers, empty-project boundary, hard limits, root identity, symlink refusal and separate store markers. A real subprocess verifies the exclusive store lock. No source data or private corpus is used.

The fault-feature tests also run child processes that exit after generation sync, before pointer rename and after rename. Reopening observed both projects in the same old or new batch as expected for each injected stage. Injected no-space/corruption failures before commit preserve the old batch. An injected directory-sync failure after rename returns `PublicationIndeterminate`, blocks new reads and writes, and permits a consistent reopen; an earlier held snapshot remains an old view. A controlled snapshot/failure race first failed without the final latch check and then passed with it; the red run was observed but its raw output was not saved. Tests also revalidate a batch on reopen under the supplied limits.

[receipt.json](receipt.json) records the two native macOS correctness suites, input and raw stream hashes, and content-addressed local paths for the actual test executables, saved immediately after each run. Default batch tests were 9/9 and feature-gated batch tests 13/13. Additional existing path-index suites are included in the streams; source paths and fixture identities are synthetic. Each run used a 3.5 GiB sampled free-space reserve, not a system quota, checked at 0.5-second intervals. No benchmark or profiling was performed.

The controlled process exits are not a physical power-loss test or an `F_FULLFSYNC` guarantee. Filesystem sync/rename, source-root identity and crash behavior are only observed on this macOS host; Linux and Windows are unimplemented and unverified. Same-UID adversarial concurrent filesystem renames are not excluded. The full product and all 80 product acceptance cases remain unverified.
