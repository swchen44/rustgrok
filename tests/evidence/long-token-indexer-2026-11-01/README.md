# Original indexer: two independent long-term failure cases

These synthetic public inputs were built under `/tmp/rustgrok-long-public`, independently of the 3,969-byte search benchmark. Both ran the fixed OpenGrok 1.14.20 indexer with the JDK, ctags, command, input hashes, exit codes and file-level logs recorded in result.json. Each project contained exactly one input file; no enterprise source was read. Each process returned exit **0**, yet each log reported `ERROR addFile()` and `1 failures (100.0%) while parallel-indexing`. A separate Lucene MatchAllDocs inventory showed three live metadata documents with null stored `path`, and the corresponding path query returned zero hits. An exit code of zero is therefore not evidence that the source file was indexed.

- `split.c`: 32,765 ASCII `a` followed by U+10400 and newline. The original file-indexing attempt failed with `IndexOutOfBoundsException` in `PlainFullTokenizer.yylex`, before the scorer could rely on a term. The separate in-memory token probe's unpaired surrogate and 32,768-byte BytesRef do **not** establish the cause of this different indexer exception.
- `utf8-over.c`: 11,000 CJK `中` characters and newline. The term is 11,000 UTF-16 units but 33,000 UTF-8 bytes. The original logged `IllegalArgumentException` for an immense `full` term exceeding Lucene's 32,766-byte limit, and the source file was not returned by the path query.

The G1 candidate now rejects both the surrogate-split boundary and terms whose adapted bytes exceed the Lucene limit, rather than silently indexing a different token. This is fail-closed experimental behavior; it does not reproduce the original's process exit or claim that silently missing a file is an acceptable correctness or performance outcome. These observations do not establish the behavior of other languages, configurations, inputs or future versions.
