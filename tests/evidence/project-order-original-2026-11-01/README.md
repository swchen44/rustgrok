# Original selected-project ordering and pages

The independently executed original OpenGrok service used one isolated copy of the retained pristine public-corpus index. Original configuration defaults were preserved; only `dataRoot` was pointed at the copied index, and the connector was bound to a new loopback port. No index concurrency or project settings were changed to force order. The input capture's complete tree hash before and after was identical, and result.json records original index-file hashes and capture/configuration hashes. Response bodies are raw; each query was made twice in one process. Session tokens were not recorded.

For `path=main` and `full=main`, requests with alpha then beta and beta then alpha produced the same raw path order for each query in both repetitions. On this index, the `start=0,1,2` single-hit pages match the corresponding prefix of `start=0,maxresults=10`. The FULL scores used to interpret the tie are documented separately in `tests/evidence/lucene-single-term-2026-11-01`; no inference is made that these document IDs are stable across reindexing. Fixed upstream SearchEngine.searchMultiDatabase builds its MultiReader with project names in Java TreeSet order. Project grouping in the later G1 candidate follows that source rule without changing or sorting oracle response bodies, but per-project document insertion order remains candidate-owned.

This is a small, single-index, single-process observation, not complete compatibility, broad repeatability, or a performance test. Reproduction needs an independently verified capture and equivalent copied Tomcat context. `tests/evidence/project-order-boundaries-2026-11-01` includes a separate rerun with zero-sized and out-of-range pages.

The equivalent current reproducibility helper is `python3 tools/capture_project_order.py --capture CAPTURE_DIR --output NEW_EXTERNAL_DIR`; it also captures the two additional boundary cases recorded in the separate boundary evidence.
