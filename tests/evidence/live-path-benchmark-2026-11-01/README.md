# Live path-only HTTP comparison: blocked

The independent OpenGrok 1.14.20 JDK/Tomcat server and Rust release server ran simultaneously on the same Mac against the same 3,969-byte public source corpus. Original index configuration was changed to `allowMostPopular=false` because that functionality was explicitly deferred; this is **not** the original default. The exact query, original and candidate status/headers, body files, configuration, versions, hashes, Java flags, index sizes and sampled process RSS/CPU are in this directory. The two returned HTTP 200 and their ordered response bodies matched except for top-level `time`. The original returned `Set-Cookie: JSESSIONID=…; Path=/source; HttpOnly`, while the candidate did not. The token is redacted in the committed report and no token is needed to reproduce the observation.

The then-conservative gate was `BLOCKED_SESSION_BEHAVIOR` and collected **zero timed samples** in the recorded run. The original's fixed source `opengrok-indexer/src/main/java/org/opengrok/indexer/authorization/AuthorizationFramework.java:528–532` creates a session while checking an entity; a second original request carrying the returned cookie produced HTTP 200 and no new Set-Cookie, with the body unchanged except `time` (see session-followup.json and raw bodies). Other session semantics remain unverified, and the candidate has not replicated even this observed behavior. Disabling sessions or fabricating a cookie would not establish equivalent behavior. Next work must test first and cookie-bearing follow-up requests and implement the applicable semantics before a same-function comparison can proceed.

An earlier exploratory run collected 200 timing samples before the session-header mismatch was detected because that earlier gate only checked bodies and content type. Those samples are **invalid for a same-function comparison** and are not presented as a performance result. Their unredacted local raw records remain only in `/tmp/rustgrok-issue7-ineligible-raw-run` with access restricted to the current user; they are not release evidence and contain expired local session tokens. That gate had tests for the mismatch and fail-before-sampling behavior; later session handling and subsequent measurements are recorded in live-path-benchmark-matched-2026-11-01. No p50/p95/p99 speed claims are made.

The original index contains 439,863 bytes and the candidate JSON index 5,414 bytes, including different feature coverage; they are not equal-function storage comparisons. The 200 ms resource samples are snapshots, not peak usage, and background load, power and OS caches were not controlled. This single-result path query cannot assess ranking, other API methods, browser behavior, 5-user production load or the approximately 500 MB workload. Issue #7 remains open.

To repeat, first create a fresh isolated capture with `tools/capture_opengrok_baseline.py` and the matching scan index using `experiments/search-spike`. Then run `python3 tools/run_live_path_experiment.py --oracle-capture CAPTURE_DIR --candidate-index INDEX_JSON --corpus PUBLIC_CORPUS --output NEW_EXTERNAL_DIR`. The later runner builds fresh indexes in an isolated output directory and verifies the original capture remains unchanged; see the newer evidence README for its current command and scope. The recorded candidate index hash is in metadata.json. The runner was re-executed with the recorded inputs and produced the same blocked session result. HTTP header comparison ignores only Date, Content-Length, and Connection; any Set-Cookie causes a conservative block until session semantics are implemented and validated.
