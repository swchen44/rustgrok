# OpenGrok-based integration and browser test plan

This plan implements the user's request to use the pinned OpenGrok tests as a reference. The original source is OpenGrok 1.14.20, commit `3ca9d73ebb0ddb5560fbc7631322d29d9fdc2ec3`. The seven specific source paths and SHA-256 values are in [source-provenance.json](../evidence/upstream-integration-2026-11-03/source-provenance.json), checked against the existing pinned source inventory. GitHub [#6](https://github.com/swchen44/rustgrok/issues/6) tracks the search slice and [#5](https://github.com/swchen44/rustgrok/issues/5) its reference corpus. These tests extend the existing WP-A08/B01/B02 work and inform future WP-C07–C10 and WP-D01–D08; no existing issue or 80-item product test is declared complete by a subset.

## Actual test levels and provenance

- `opengrok-indexer/src/test/java/org/opengrok/indexer/analysis/PathTokenizerTest.java`, `testIncrementToken`, is a JUnit **unit test** of `alpha/beta/gamma/delta.ext`; its loop stops at the dot and does not check the extension. The Rust public-crate integration test uses this upstream scenario, but obtains the complete stream independently using the fixed original `CompatibleAnalyser`. [Raw capture and receipt](../evidence/upstream-integration-2026-11-03/README.md) include the original `ext` token. `crates/analysis/tests/upstream_path_integration.rs` is an adapted upstream test and retains its CDDL header, copyright, license and source. This does not test a product service or browser.
- `opengrok-indexer/src/test/java/org/opengrok/indexer/index/IndexerTest.java`, `testIncrementalIndexAddRemoveFile`, sets up a project and `IndexDatabase`, updates it after adding/removing a file and checks change events. `SearchEngineTest.java` builds an index from a test repository and exercises search fields, sorting and result caps. They include component integration tests; accessor tests in the same class remain unit tests.
- `opengrok-web/src/test/java/org/opengrok/web/api/v1/controller/SearchControllerTest.java` builds an index and uses JerseyTest with a Grizzly container and HTTP requests. It checks results, repeated-request ordering, line numbers, page counts, default page size, negative values, overflow and beyond-end pages. `FileControllerTest.java`, `DirectoryListingControllerTest.java` and `HistoryControllerTest.java` exercise file content/definitions, directory entries and history paging. These are HTTP/controller integration tests, not installed-product browser e2e.
- The pinned source configures JUnit, Maven Surefire and Jersey/Grizzly; upstream CI invokes `./mvnw -B -V verify` via `dev/main`. The tools module also has pytest tests, some using mocks. This is source inspection; no upstream suite was executed for this plan.
- A source search for browser frameworks including Selenium/WebDriver, Playwright, Cypress and Puppeteer found no explicit browser e2e suite in the inspected text files; it does not rule out external repositories or unsearched binaries. The browser scenarios below are proposed Rustgrok tests based on observed original behavior, not a claim that OpenGrok ships equivalent browser automation.

The seven selected source files carry CDDL-1.0 headers and their original copyright. Preserve original license, headers, notices, commit and source-delivery conditions on copies or adaptations. Independently authored Rust tests use the confirmed MIT `swchen44` notice; other fixtures and dependencies retain their own terms. The [synthetic source-path fixture](../fixtures/upstream-integration-2026-11-03/source-paths.tsv) is independently authored for this test and contains no upstream source or enterprise data.

## Executed component integration

`cargo test --manifest-path crates/analysis/Cargo.toml --locked --offline` invokes the public library API from separate Rust integration-test crates. One test compares all six tokens, positions and UTF-16 offsets against the captured original stream. Another reads C/Python/JavaScript logical paths and source text from the synthetic fixture: two `main` paths are recognized by their tokens, and two previously unsupported Unicode paths are now accepted within the documented subset. Unverified inputs remain explicit errors. It does not index source contents, implement query parsing or search a service. `python3 -m unittest discover -s tests/contract -p test_upstream_integration_evidence.py -v` verifies fixture and receipt hashes, upstream source inventory and 74 original classpath jar identities. Scope: FR-001/002/008/021/022; RST-002/003 and SRC-001 only as future full-test references. The complete matrix tests remain **planned**.

## Planned / blocked: product entry points not implemented

These are specifications, not executable stubs or skipped tests. Each requires a real Rustgrok product entry point and isolated synthetic/public fixture. Record actual OS, inputs, configured helpers, commands, exit/status, original and Rust raw responses and failures; never report a missing entry or skip as pass.

1. **Indexer full and incremental** — based on `IndexerTest.testIncrementalIndexAddRemoveFile`; FR-008/009/021, WP-C07/C09, SRC-001/002 and RST-009. Given two projects and public C/Python/JS source, create an index and assert the original and Rust path/document coverage for a fixed query. Add a file and reindex; assert the new result appears. Remove it and reindex; assert the result disappears. Verify source bytes are unchanged by the indexer. Separately verify new Rustgrok Q8: while the replacement generation builds, queries see the last complete generation; injected failure/cancel does not publish a partial generation and a completed generation switches as a unit. Q8 is an additional product requirement, not claimed coverage of the upstream test. **Partially implemented:** a single-project path-postings library has component integration tests, constrained macOS durable recovery and restricted source traversal with a nested-Git fixture. A development CLI now has subprocess e2e for this restricted path flow; it is not the installed multi-project product. **Blocked:** complete product source discovery/filter compatibility, complete Q8 publication across all necessary data and ranked search entry still do not exist.
2. **Search HTTP** — based on `SearchControllerTest`; FR-001/003/007/011, WP-C09/C10/D01, REF-002, PRJ-001, API-001 and API-003. Using the same public corpus/configuration, query one project and both projects; compare raw status, JSON types, `resultCount`, ordered paths and matching lines against independently run original. Test `start=0/maxresults=1`, a page beyond total, negative start/maxresults/maxhitsperfile, overflowing start+maxresults, and default page size against actual configuration. Preserve original order and report differences, including ties; do not sort or mask them. Execute original and product services one at a time, preserving their raw observations. **Blocked:** no product HTTP/search entry exists.
3. **Browse and history HTTP** — based on `FileControllerTest`, `DirectoryListingControllerTest`, `HistoryControllerTest`; FR-005/006/011, WP-C10/D02/D03, API-001 and relevant UI/SCM tests. On a deterministic public repository, fetch content and compare bytes to the corresponding live/SCM source branch, list a directory and compare entries, then request a known history page and compare revisions/order with the original. Source reading follows Q9; do not invent a whole-source reading snapshot. **Blocked:** product browse/history/SCM handlers absent.
4. **Browser end to end** — proposed Rustgrok test informed by original UI/routes, not an existing upstream browser suite; FR-004/005/007/012/013/017, WP-C10/D02/D05, UI-001/002, SEC-002/005 and API-002. Install or start the real product with two public projects; open its original-style page in a real browser, choose a project, search, open a result, verify line anchor/xref and raw/download; compare DOM, URL, visible interaction and screenshots to a same-config original in the same browser/environment. Reindex while searching, verify old complete generation remains until publication, then new results. LAN is search/browse; management API/page must remain host-local, and unresolved Q15 page actions are not assumed. Record results per supported platform: native macOS first, then Ubuntu 24.04 amd64 and Windows 11 x64 independently. **Blocked:** no complete product service or original-style UI exists; the single-project path CLI does not establish full generation publication.

Use only generated or vetted public data. Ctags and SCM helpers are authorized external programs; D19 requires necessary helpers to ship with the product and their source, version, license and native platform capabilities to be recorded. Do not introduce a product JVM. Run one work item at a time. No performance measurement is part of these cases.
